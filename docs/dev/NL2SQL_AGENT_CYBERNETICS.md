## 0. 为什么用控制论看问数 Agent

工程控制论的核心命题是：

> 「控制理论主要研究系统状态的运动规律和改变这种运动规律的方法和可能性。前者为分析，后者为综合（设计）。分析是基础，综合是目的。」——§1ls

把这句话翻译到问数 Agent：**用户问题（自然语言）是输入，SQL/数据洞察是输出，StateGraph 是改变「输入→输出」运动规律的综合手段。** 一个问数系统天然具备控制系统的全部要素——反馈（执行失败重试）、校正（SQL 重写）、估计（RAG 召回）、监督（人在回路）、容错（执行器降级）。因此用控制论看它，不是修辞，而是**最贴切的工程语言**。

> 「要注意关联必须以数学形式定下来，也就是要定量，不然就没有控制论。」——序§8

这条语录直接给本文定调：**所有结论必须可度量**——准确率、终止性、成本，而不是「我觉得这个架构好」。

## 1. 系统建模：把问数 Agent 抽象成控制系统

### 1.1 黑箱定义（输入 / 输出 / 边界）

```
                ┌──────────────────────────────────────────┐
 自然语言问题 ──▶│                                          │──▶ SQL / 结果 / 图表报告
 多轮上下文   ──▶│          问数 Agent（被控对象）            │──▶ SSE 流式 token
 人工反馈     ──▶│                                          │
                └──────────────────────────────────────────┘
                     ▲          ▲            ▲
                     │          │            │
                业务数据库   向量库(RAG)    LLM    ← 边界外（系统假设其行为，不控制其行为）
```

**边界之外**的系统，问数 Agent 只能**假设**其行为并**兜底**其失效：

| 边界外因素 | 系统的假设 | 对应兜底（反馈/校正） |
| :--- | :--- | :--- |
| LLM 返回符合格式 | 大多数时候对 | 语义一致性校验 + 错误修复重试 |
| 业务 DB 可连可读 | 连接稳定 | 数据源校验在早期失败（早退，不发散） |
| 向量召回相关 | 相似度排序有效 | 相似度阈值 + 混合检索（向量+关键词） |

> **工程含义**：bug 若源于「边界外不可控」但系统没兜底，才是设计缺陷——这才是要修的。LLM 偶发乱码是边界外，系统因此崩溃是边界内缺失。

### 1.2 系统类型判定（推理四步法 Step 1-3）

按《工程控制论》推理四步法对问数 Agent 分类，**类别决定工具集**（准则 η₁）：

| 步骤 | 判定 | 依据 | 指向的工具集 |
| :--- | :--- | :--- | :--- |
| Step1 系统类型 | **离散** | 图执行是事件驱动，节点间是跳转不是连续演化 | 有限状态机 / 自动机（域Ⅵ §17） |
| Step2 线性度 | **本质非线性** | LLM 输入输出关系不可线性化，无固定工作点 | 不能用线性化；用**图/逻辑**方法定性分析 |
| Step3 随机性 | **强随机** | LLM 概率性输出 + 检索概率性召回 | 估计/滤波（域Ⅴ）、统计最优 |

> 「我们说某系统是线性系统，意思只是它的某些主要性能可充分精确地用线性系统近似代表。」——§1.4
>
> 问数 Agent 的 LLM 环节**不满足**这条——它无法被线性近似。这正是为什么问数系统不能靠「调一个参数」变好，而必须靠**反馈闭环 + 估计 + 容错**来驯服非线性。

**结论**：问数 Agent 是一个「离散 + 本质非线性 + 强随机」的信息控制系统。对应的控制论工具集是：
- **反馈与校正**（域Ⅲ）——重试、SQL 重写
- **估计与滤波**（域Ⅴ）——RAG 召回是「带噪测量」，证据融合是「滤波」
- **递阶控制**（域Ⅵ §21）——Planner（上层决策）→ 步骤执行器（下层执行）
- **逻辑控制/自动机**（域Ⅵ §17）——StateGraph 的条件边就是有限自动机
- **容错与冗余**（域Ⅵ §19）——多执行器降级（Docker→Local→AI 模拟）
- **信息论**（域Ⅵ §20）——schema 注入的 token 预算 = 信道容量

## 2. 系统分析：四条技术路线 = 四种控制架构

把调研的 9 个项目归为 4 条路线。**用控制论的眼光看，它们是 4 种不同的控制结构**，各有其稳定性、反馈、信息效率特征。

### 2.1 路线①：单步 Agent + Tool —— 开环控制

**代表**：text-to-sql-agent、LangChain-SQL-Agent-for-dynamic-data-visualization、langchain-sql-agent-guide

LLM 自主决定调用哪个 tool（list_tables → schema → query → check），一次 agent 循环内完成。

**控制论画像**：

```
问题 ──▶ [LLM 自主循环] ──▶ SQL/结果
              ↑__________________|
            （隐式自我修正，无显式反馈通道）
```

- **结构**：近似**开环**——没有独立的「测量-比较-校正」通道，错了全靠模型在 `max_iterations` 内自己领悟。
- **稳定性**：弱。无显式终止保障，依赖迭代上限。
- **信息效率**：低。把整个 schema 塞进上下文，token 浪费严重。
- **适用**：demo、学习、schema 极小的场景。
- **不适用**：生产、复杂业务口径、多表。

> 这是工程控制论里典型的「未建模动态主导」结构——简单但鲁棒性差，一旦 schema 变大或业务变复杂就「发散」。

### 2.2 路线②：显式多步 Graph —— 多重闭环监督控制

**代表**：**当前 DataAgent**（Java/Spring AI Alibaba Graph）、QueryWeaver（Python/FastAPI + LiteLLM）、SQLBot（Python/FastAPI + Vue 3）

> 📌 **栈勘误（源码核实）**：QueryWeaver 与 SQLBot 后端均为 **Python/FastAPI**，并非早期认知的 TS/Node 或 Go。二者是本路线最值得对照的两家——但在 Java/Spring AI 技术栈上，原则是**抄设计（机制）不抄代码（语言）**：SQLBot 的 AST 三层只读校验、QueryWeaver 的 HealerAgent 自愈与 FalkorDB 图检索，都可在 `jsqlparser` + Spring AI `StateGraph` 上等价复刻（见 §4.3）。详见 [QueryWeaver 卡片](../research/queryweaver.md)、[SQLBot 卡片](../research/sqlbot.md)。

把流程拆成确定节点链，条件边做分支与循环。

**控制论画像**：

```
         ┌──[意图]──[估计:RAG召回]──[规划]──┐
问题 ──▶ │                                    │ ──▶ 报告
         │   ┌──[SQL生成]──[校验]──[执行]──┐  │
         └──▶│       ↑________失败________|  │
             │   [HITL 监督]                   │
             └──[Python生成]──[沙箱执行]──[分析]┘
```

- **结构**：**多重闭环**——SQL 重试是误差反馈闭环（带抗饱和上限），HITL 是监督控制，RAG 是测量前置。
- **稳定性**：强。每条重试边都有次数上限（抗饱和），可行性评估做早退（避免无效发散）。
- **信息效率**：高。Schema 召回只取 top-K 相关表。
- **可观测**：每个节点独立 trace（Langfuse）。
- **适用**：生产、流程固定的问数场景。**这是当前 DataAgent 已选的路线，且是三家中最完整的（含 HITL + Python 深度分析）。**

### 2.3 路线③：RAG 训练式 —— 在线辨识 / 自适应

**代表**：vanna

`train(question, sql, ddl, documentation)` 持续把三类知识存向量库，查询时分库检索注入。

> 📌 **版本注记（源码核实）**：vanna 2.0 已把经典 NL2SQL RAG 核心（`VannaBase`、`train()`、三库检索、`get_sql_prompt()`）**整体移入 `src/vanna/legacy/`**，新 `core/` 是与 NL2SQL 解耦的通用 Agent 框架。下文借鉴均指 `legacy/` 中的 RAG 本体。详见 [vanna 卡片](../research/vanna.md)。

**控制论画像**：这是**系统辨识**（域Ⅴ §16 自寻最优）的变体——系统不在「运行时校正单次输出」，而是「用历史样本持续改进模型本身」。准确率随样本量**单调上升**。

- **结构**：**自适应/学习**——把「准确率」当作被控量，用样本反馈逼近最优 prompt 装配。
- **代价**：冷启动需标注，大库 DDL 易超长。
- **价值**：这是 vanna 最值得借鉴的一点——**让系统越用越准**，而不是停留在「每次都从零猜」。

### 2.4 路线④：DB 原生 —— 测量前置 / 传感下沉

**代表**：pgai

把 embedding 调度与语义目录下沉到数据库层（vectorizer worker + semantic catalog）。

> 📌 **栈勘误（源码核实）**：常被表述为「DB 内 embedding」，但源码事实是——vectorizer worker 仍**把数据拉出库**调 embedding API，真正下沉到 DB 的只是**调度与一致性状态**（`FOR UPDATE SKIP LOCKED` + advisory lock 队列、行/语句级触发器自动入队）与 **semantic catalog**（PG 事件触发器跟随 DDL 自维护，应用层做不到的零漂移）。扩展仅依赖 `pgvector + plpython3u`，**不依赖 TimescaleDB**。详见 [pgai 卡片](../research/pgai.md)。

**控制论画像**：把「传感器」（向量化调度、schema 描述生成）的**状态管理**从应用层下沉到数据源层，数据变更经触发器自动入队同步。

- **结构**：**测量通道前置**——检索质量的一致性由 DB 保证（事件触发器零漂移），而非依赖应用层轮询。
- **代价**：耦合单一 PG；pgai 已于 **2026.02 停止维护**；不适合多异构数据源；"DB 内 embedding" 是对其架构的常见误读。
- **启示**：其 semantic catalog「事件触发器自维护 schema 描述」的思路可在应用层复刻（如 DataAgent 监听 DDL 变更刷新向量库）；但对多数据源场景，应用层向量库仍是更优解（见 §4.3）。

### 2.5 四路线横向对比（控制论维度）

| 维度 | ①开环Agent | ②多步Graph | ③RAG训练 | ④DB原生 |
| :--- | :--- | :--- | :--- | :--- |
| **反馈结构** | 隐式 | 多重显式闭环 | 学习型 | — |
| **稳定性保障** | 弱（迭代上限） | 强（抗饱和+早退） | 中 | 强（DB一致性） |
| **信息效率** | 低（全量schema） | 高（召回top-K） | 高（分库检索） | 高（DB内） |
| **可观测性** | 弱 | 强（节点trace） | 中 | 中 |
| **自适应能力** | 无 | 无 | **有** | 无 |
| **多数据源** | 单 | 多 | 多 | 单一DB |
| **代表项目** | LangChain×3 | DataAgent/QueryWeaver/SQLBot | vanna | pgai |

## 3. 七条工程准则在问数 Agent 的落地

工程控制论的七条工程近似准则（η₁–η₇），逐条映射到问数 Agent 的设计决策：

| 准则 | 控制论含义 | 在问数 Agent 的落地 |
| :--- | :--- | :--- |
| **η₁ 分类定方法** | 类别决定工具集 | **意图识别节点**先分类（闲聊/可分析/不可行），再选处理路径。不可行早退，避免无效计算。 |
| **η₂ 最少自由度** | 只保留本质变量 | 节点单一职责；**不要把全量 DDL 塞 prompt**（vanna 的超长 DDL 教训）；schema 只召回 top-K 相关表。 |
| **η₃ 线性化有效区间** | 近似在何种前提成立 | 「LLM 大多数时候对」是有界假设；超出区间（复杂 JOIN、口径模糊）就失灵——必须用校验+重试兜底，而非假设它永远对。 |
| **η₄ 主导因素优先** | 主导极点定核心动态 | **schema 召回准确率主导 SQL 准确率**——这是系统的「主导极点」。优化应先打这里，而不是先调报告措辞。 |
| **η₅ 先稳后优** | 不稳不谈性能 | **先保证终止/收敛/安全，再追准确率**。重试上限、AST 只读校验、行数限制，都是稳定性保障，优先级高于 prompt 调优。 |
| **η₆ 有限区间** | 变系数用有界近似 | 重试次数、超时、返回行数、token 预算、成本，**全部必须有界**。无界重试 = 发散。 |
| **η₇ 近似可验证** | 工程实践是最后标准 | **任何改动必须能被评测集或 trace 验证**。没有评测集的「优化」是盲调。 |

> 这七条不是装饰，是**做技术选型时的决策坐标系**。下文 §4、§5 的每一个决策，都标注了它遵循哪条准则。

## 4. 系统设计：基于 Spring AI Alibaba Graph 的构建蓝图

### 4.1 为什么选 Graph 而不是开环 Agent（η₁ 推导）

准则 η₁「分类定方法」：问数场景的**流程是固定的**（意图→检索→生成→执行→报告），不是开放探索。流程固定 → 确定性编排优于 LLM 自主 tool calling。

Spring AI Alibaba Graph 提供 `StateGraph` + 条件边 + `interruptBefore` + 状态快照恢复，天然支持路线②的多重闭环。这正是路线①（开环）做不到、而当前 DataAgent 已验证可行的关键能力。

### 4.2 推荐节点拓扑（控制论标注）

```
[意图识别] ──(off-topic)──▶ 拒答                 ← η₁ 分类定方法
    ↓
[多轮上下文改写]                                  ← 测量降噪（域Ⅴ）
    ↓
[Schema召回: top-K表 + 外键关系子图]              ← η₂ 最少自由度 + η④ 主导因素
    ↓
[RAG证据召回: 知识库 / DDL / SQL样例 三库]         ← 路线③自适应（域Ⅴ§16）
    ↓
[可行性评估] ──(不可行)──▶ 追问澄清               ← η₅ 先稳后优（早退）
    ↓
[Planner] ──▶ 步骤计划                            ← 递阶控制上层（域Ⅵ§21）
    ↓
[Plan校验] ──(invalid)──▶ 回Planner               ← 闭环校正
    ↓
[HITL审核] interruptBefore                         ← 监督控制（域Ⅵ）
    ↓
┌─ SQL步骤: [SQL生成]→[AST只读校验]→[语义校验]→[执行]
│           ↑_________________失败________________|
│           └─ [错误修复] ↻ max N                 ← 反馈校正+η₆抗饱和
├─ Python步骤: [代码生成]→[沙箱执行]→[分析]
└─ 报告步骤: [报告生成] 流式 SSE
```

> 加粗标注的每一处，都是控制论概念在代码里的落点。**节点 = 环节，Dispatcher = 比较器，共享 State = 状态空间，重试边 = 误差反馈闭环，`interruptBefore` = 监督控制。**

### 4.3 四个关键设计决策（控制论推导）

**决策一：Schema 策略 = 信息论（域Ⅵ §20）**

> 「信息率决定控制精度上限。」

LLM 的上下文窗口是**有限带宽的信道**。把全量 DDL 塞进去 = 信道过载 → 噪声淹没信号 → SQL 出错。

- 小库：全量 DDL（信道充裕）。
- 大库：**向量召回 top-K 表 + 外键关系子图**（借鉴 QueryWeaver 的 FalkorDB 图检索）——这是「信道编码」，只传相关信号。QueryWeaver 的四路并发召回值得照搬：表向量 top-3、列向量 top-3、FK 邻域、`allShortestPaths(*..6)` 找桥接表（解决"用户没提中间表但要 JOIN"）。详见 [QueryWeaver 卡片](../research/queryweaver.md)。
- **不要**像 vanna 0.x 那样靠 `max_tokens` 硬截断 DDL（丢的是随机片段，不是冗余）。

**决策二：自愈循环 = 反馈校正（域Ⅲ）+ 抗饱和（η₆）**

SQL 执行失败 → 错误信息回灌 → 重写 → 重试，最多 N 次。

- 这是经典的**误差反馈闭环**。
- N 必须有界（η₆ 抗饱和）——否则发散烧 token。
- 用 Graph 的**循环边 + `attempts` 状态字段**实现，比单步 agent 隐式重试**可观测**：每轮 trace 清晰，便于调参和归因。借鉴 QueryWeaver 的 `heal_and_execute` ×3——循环外构造一次 prompt，循环内把每轮新错误以 user feedback 累积进同一 conversation（LLM 能看到"上轮改成 X 又报 Y 错"），返回 `{success, sql, attempts, final_error}`，`attempts` 作为一等状态字段。详见 [QueryWeaver 卡片](../research/queryweaver.md)。

**决策三：安全护栏 = 先稳后优（η₅）**

> 「对控制系统的第一个要求是稳定性。」——§4

执行 SQL 前，用 `jsqlparser`（Java 版 sqlglot）做 **AST 级只读校验 + 危险函数黑名单 + 表名白名单**（不信 LLM 返回的表名，借鉴 SQLBot）。SQLBot 的 `check_sql_read()` 三层防御值得逐层照搬：① 首词黑白名单（`SELECT`/`WITH` 放行，DML/DDL 拦截）；② 危险模式正则（`DANGEROUS_PATTERNS`）；③ sqlglot AST 节点类型（`Insert/Update/...`）+ 库特定危险函数字典（`DS_SPECIFIC_DANGEROUS_FUNCTIONS`）。表名白名单的关键是**用 AST 重解析真实表名**，与 LLM 自报的 `tables` 字段解耦做差集。详见 [SQLBot 卡片](../research/sqlbot.md)。

这**不是性能优化，是稳定性保障**——它防的是「系统对生产库造成不可逆破坏」。按 η₅，它的优先级**高于**一切精度优化。生产上线这是硬门槛。

**决策四：RAG 训练库 = 在线辨识（域Ⅴ §16 自寻最优）**

新增 `sql_examples(question, sql, agent_id)` 向量表，成功 SQL 反哺入库，查询时作为第三路召回（借鉴 vanna 三库训练）。

- 这是**系统辨识**：用历史样本持续逼近最优 prompt 装配，准确率随使用单调上升。
- 是当前 DataAgent 相对 vanna **最大的可补强点**，投入小、收益大。

### 4.4 HITL = 监督控制

金融、医疗、生产决策等场景，不能让 AI 全自动跑。`HumanFeedbackNode` 用 `interruptBefore` 把图「冻结」，等人 approve/reject，再恢复或回退——这是控制论里**监督控制**（机器做日常决策，人在关键节点把关）的标准实现。

## 5. 系统优化：当前 DataAgent 的差距与增强路线

按准则 η₅「先稳后优」给增强项**排序**：稳定性类 > 鲁棒性类 > 精度类。**不能先调精度再补安全**。

### 5.1 稳定性 / 安全类（必须先做）

| 增强项 | 控制论原理 | 参考来源 | 风险 | 投入产出 |
| :--- | :--- | :--- | :--- | :--- |
| **AST 级 SQL 只读校验 + 危险函数黑名单 + 表名白名单** | η₅ 先稳后优 | SQLBot(sqlglot) | 中 | 🔴 极高 |
| **X-API-Key 鉴权 + 行级权限改写** | η₅ | vanna/SQLBot | 中 | 🔴 极高（多租户必备） |
| **重试/超时/行数/成本全局有界** | η₆ 有限区间 | 通用 | 低 | 🔴 高 |
| **破坏性操作（DML/DDL）转 HITL 二次确认** | η₅ | QueryWeaver | 中 | 🟡 高 |

### 5.2 鲁棒性类

| 增强项 | 控制论原理 | 参考来源 | 风险 | 投入产出 |
| :--- | :--- | :--- | :--- | :--- |
| **Schema 外键关系建模（图检索）** | η₄ 主导因素 | QueryWeaver(FalkorDB) | 中 | 🟡 高（多表 JOIN） |
| **执行器容错降级链**（Docker→Local→AI模拟） | 域Ⅵ§19 容错冗余 | 已有，需补全 | 低 | 🟡 中 |
| **schema 自动语义描述**（减少人工标注） | 域Ⅴ 辨识 | pgai(semantic catalog) | 中 | 🟡 中 |

### 5.3 精度 / 自适应类

| 增强项 | 控制论原理 | 参考来源 | 风险 | 投入产出 |
| :--- | :--- | :--- | :--- | :--- |
| **SQL 样例 RAG 训练库（三库召回）** | 域Ⅴ§16 在线辨识 | vanna | 低 | 🔴 极高 |
| **Prompt 优化（planner/sql-generator/report）** | η₇ 可验证 | 已有框架，需接评测 | 低 | 🟡 高 |
| **混合检索调参（向量+关键词融合权重）** | 域Ⅴ 滤波 | 已有 HybridRetrieval | 低 | 🟡 中 |

> **一句话**：当前 DataAgent 在「Graph 编编 + HITL + Python 分析 + MCP」上已是 9 项目中最完整的；真正该补的是 §5.1 的三件生产级能力——**SQL 样例 RAG 训练库、AST 安全护栏、行级权限**。

## 6. 可验证性：没有评测的优化都是盲调

准则 η₇ 与序§8「关联必须定量」共同要求：**所有优化必须建立在度量之上**。

建议建立的评测维度：

| 维度 | 度量 | 控制论对应 |
| :--- | :--- | :--- |
| **执行成功率** | 生成的 SQL 能否执行通过 | 系统基本功能 |
| **语义正确率** | 结果是否回答了用户真问题（需人工标注集） | 控制精度 |
| **终止性** | 是否在有限步内收敛（无死循环/超时） | 稳定性（η₅） |
| **成本** | 平均 token 消耗、平均耗时 | η₆ 有限区间 |
| **鲁棒性** | schema 变更 / 边界输入下的退化曲线 | 对模型失配的容忍 |

> **没有评测集，就不要做 prompt 调优和 RAG 调参**——那是在没有示波器的情况下焊电路。

## 7. 假设、局限与置信度

### 7.1 工程假设（结论成立的前提）

1. 问数场景的流程是**相对固定**的（意图→检索→生成→执行→报告），非开放探索。若未来要支持「自主探索型」agent，路线②需向路线①退化部分节点。
2. LLM 通过 OpenAI 兼容接口接入，行为概率性但**可重复调用**（保证反馈闭环可执行）。
3. 业务数据库**可连可读**，连接异常应早退而非重试。

### 7.2 结论失效条件

- 当 schema 极小（单表几列）时，路线①的开环 agent 成本更低，路线②的复杂图编排是**过度设计**（违反 η₂）。
- 当业务口径极度依赖人工定义（强语义层）时，纯 RAG 训练（路线③）不够，需引入显式指标层（metric layer）。
- 当数据源是单一 PG 且需极致 embedding 一致性时，路线④（pgai 式下沉）可能更优——但 pgai 已停维，需自承担维护风险。

### 7.3 置信度

| 结论 | 置信度 | 依据 |
| :--- | :--- | :--- |
| 四路线归类与控制论画像 | **High** | 基于源码级调研（vanna/SQLBot/QueryWeaver）+ 控制论概念直接对应 |
| 当前 DataAgent 的优势判断 | **High** | 基于 `ARCHITECTURE.md` 源码级流程图 |
| 增强路线的优先级排序 | **Medium** | 遵循 η₅ 排序原则，但具体优先级取决于业务场景 |
| 构建蓝图的节点拓扑 | **Medium** | 融合当前实现 + 竞品精华，需结合实际业务验证（η₇） |
